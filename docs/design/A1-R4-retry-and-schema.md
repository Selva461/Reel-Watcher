# A1 + R4: a retry cap with visible failure reasons, and schema safety (design, not approved)

Base: `origin/ccr-d0c0b070-bdpssy` at f6a3f29 (1.3.11, versionCode 18). Planning only.

## Order: R4 first, then A1
1. **R4-1 (fixtures and round-trip tests, tests only)** is the safety net. It proves that every released library still loads and saves without losing a field. A1 adds new reel fields, so the fixtures must exist first: they then show that A1's change keeps old fields and that its new fields survive.
2. **R4-2 (schema_version and the "newer library" screen)** must be in released builds *long before* any future non-additive change. Only versions that contain the check are protected. S4's restore also needs this rule.
3. A1 is purely additive and needs **no** schema bump, so it can follow straight after.

## R4: schema safety

### Rules
- **Additive change** (no bump): a new optional field that old code ignores and keeps. The page keeps unknown keys: `loadDb` does `{...d}` and reel objects are kept whole (local.js:83). Every A1 field falls in this class.
- **Bump `schema_version`** for a removed or renamed field, or a field whose type or meaning changes.
- **reels.json:** add the top-level `"schema_version": 1`. The page sets `db.schema_version = SCHEMA` (a new constant in local.js) in `loadDb` when it is missing, so it is written on the next save. Versions 1.3.6 to 1.3.11 keep unknown top-level keys (checked at each tag: `db = { ...d, ...}`), so an older app preserves it.
- **shots.json** already has `v: 1`, written by every version since it was created (shots.js:12/26 at v1.3.6..1.3.11). **But old shots.js rebuilds `state = {v:1, seen, reels}` and drops every other top-level key.** So: use the existing `v` as the version, and **never add top-level keys to shots.json**. New data goes only inside the `seen` and `reels` entries, which are kept whole.
- **Opening a newer library.** `LibraryFile` gets a `supported` number per file (`REELS_SCHEMA = 1`, `SHOTS_SCHEMA = 1`). Inside `read()`, after `valid(main)` passes, if `schema_version` (or `v`) is greater than `supported`:
  - set the new `State.NEWER` with `locked = true`, and return "";
  - **no `.bak` restore** (that would silently roll the library back), no quarantine, no rename;
  - `write()` is refused (it already refuses while locked);
  - `startNew()` is not offered for NEWER.
  - `libraryInfo` returns `{"state":"newer","found":2,"supported":1}`.
- **The page** also checks this itself, as it already does for damage (local.js:82): `d.schema_version > SCHEMA` locks the library. A new `newerScreen()` says: "This library was saved by a newer Reel Shelf. This version (1.3.x) cannot open it safely and has not changed it. Install the newest Reel Shelf." It offers one button, "Save a copy to Downloads" (the existing `saveUnreadable`; `unreadableFile()` returns `main` while locked). Shots: `shots.js load()` must not call `libraryStartNew` for "newer". It sets `blocked = true` instead, because today it sets aside *any* unusable list (shots.js:36-37).
- `VerifyJob` reads reels.json directly (VerifyJob.java:136-138) but writes only `verify-results.json`, and the locked page never applies those results. That is harmless; leave it.
- A JUnit test asserts that the Java and JS schema constants are equal, in the same way a test keeps `app.css` equal to its copy.

### Upgrade fixtures (synthetic data only: AGENTS.md forbids real reel data)
- Released tags on disk: v1.3.6, v1.3.7, v1.3.8, v1.3.10, v1.3.11. **There is no v1.3.9 tag**, because 1.3.9 exists only on the unmerged Task 2b branch.
- Commit `tests/fixtures/library/<ver>/reels.json` and `shots.json` for 1.3.6, 1.3.7, 1.3.8, 1.3.10 and 1.3.11 (I recommend adding 1.3.10; D-R2), plus `newer/` (current, with `schema_version: 99` and `v: 99`).
- They are **generated by each tag's own page code**, not written by hand. `tests/fixtures/make_library_fixtures.py`:
  1. extracts `git archive vX android/app-shell/app/src/main/assets/local` into a temp directory;
  2. drives one fixed scenario with the phone harness: share 3 links, file a Meta AI answer, a reel that fails with `generate` (status "failed"), 2 watchlist titles with a verify result, a quote, a product, a screenshot list, and a `lastNight`;
  3. writes out what the fake `RN.store` and `RN.storeShots` received.
- The generator is run by hand when a version is released. It is not run in CI, because the shallow clone has no tags.
- **I could not find a committed 1.3.6 fixture file.** The only upgrade test I found is `test_a_library_from_the_previous_version_loads_and_saves_with_every_key_kept` (tests/test_library_safety.py:177), which uses a hand-made dict. The brief's "one real 1.3.6 fixture" may live elsewhere or on another branch.

### Tests
- **`tests/test_library_upgrades.py`**, run once per fixture version:
  - open it with the current page;
  - force a save (share one link);
  - check, by a recursive diff, that **every key path and value of the fixture is still there**, apart from an explicit per-version `EXPECTED_CHANGES` allowlist (for example `status "working"→"new"`, the `author "Media"` cleanup at local.js:85, and `Verify.migrate` rule bumps);
  - check that `schema_version == 1` was added and that `shots.json` keeps `v` and every `seen`/`reels` entry.
- **The `newer` case:** the page shows `newerScreen`, `store` and `storeShots` are never called, and the share queue is not acked.
- **JUnit `LibraryFileTest`:**
  - each fixture reads as OK;
  - `newer` gives NEWER and locked, the bytes are unchanged, no `.bak` or `.bad-*` is created, and `write` is refused;
  - a newer main next to an older valid `.bak` is **not** restored from the `.bak`.

### Rollback note
Android refuses a lower versionCode. Uninstalling first deletes the library, because `allowBackup=false`. So a rollback is **a new build with a higher versionCode that contains the old code**. That rollback build must keep the R4 check, and it must support the highest schema any released build wrote. The rule: never release a schema bump without one of these:
- a reader for the old schema in the new build, plus a down-converter, or
- `supported` raised in the rollback build too.

Ask users to make an S4 backup before a bump release.

## A1: a retry cap with visible failure reasons

### Current behaviour (verified)
- `needsWork` (local.js:277-284) has no attempt counter.
- In `startRun` (local.js:519-577), a thrown error sets `status="failed"`, `r.error`, `run.failed++`. But a failed reel still passes `needsWork`: it has no notes, `caption_read` and `video_tried` are set, the model is ready, and `material >= 30`. So every Start and every night picks it again.
- The nightly run is the same page in `NightRun.Headless` (NightRun.java:145, `#/night`) and goes through `overnightRun → startRun` (local.js:622-623). Its queue is sorted `byUsefulThenNewest` and cut to `settings.nightMax || 200`. **When more than nightMax reels are waiting, the oldest are starved.**
- The measured 1,2,3,4,5 `generate` calls over five runs was **not re-measured** here. The code path explains it.

### New per-reel fields (additive; missing means 0 or empty)
`tries` (failures in a row), `last_fail_at` (ms), `last_fail` (reason, at most 300 characters; `r.error` is cleared at the start of every attempt, local.js:534, and is also used for non-failures), `next_try_at` (ms). **No new `status` value:** a parked reel stays `"failed"`, which old versions already understand. On success, `tries`, `next_try_at` and `last_fail` are deleted.

### What counts as a failure
- **Counts:** any error thrown in the `startRun` try block that is not one of the exclusions below. That covers `generate` errors ("The AI model failed: ...", LocalBridge.java:~689), the "answer was not in the notes format" error (local.js:507), and a `readLocalVideo` rejection.
- **Does not count:**
  - `run.stop` or `"stopped"`: the Stop button, `onAppPause`, `stopAllWork` from the battery and heat watch (NightRun.java:149-157), and the 2b handover;
  - `/slow down/`: Instagram 429. `igFetch` already has its own run-level strikes (2, 10 and 30 minutes, then stop; local.js:344-369), and the reel already goes back to `"new"`. **This is reused, not duplicated.**
  - caption, network and YouTube problems. `readCaption` swallows them into `r.error` (local.js:446-456; YouTube reasons are in `yt_tried`), so they never throw.
- **Circuit breaker:** 3 failures in a row within one run with the same reason prefix (for example a broken model) stop the run with `run.note = "The on-phone AI failed 3 times in a row: ..."`. Only the reels actually tried are counted, so a broken model cannot park the whole library.
- **Not counted in v1:** a crash or kill in the middle of a reel (the reel is left `"working"` and reset by `loadDb`). The 2b handover force-ends a night after 20 s, which looks the same, so counting it would penalise reels unfairly. Follow-up A1-3 (D-A3): a small prefs marker set before `generate`, plus a flag set when 2b force-ends a run.

### Cap and backoff (D-A1)
- **Failure 1:** `next_try_at = now + 12 h` (so the next night, not again straight away).
- **Failure 2:** `+ 3 days`.
- **Failure 3:** parked. It is never picked automatically; only by hand.
- `CAP = 3`, `BACKOFF_H = [12, 72]`. They live in one pure helper, `Notes.retryAfter(tries)` (testable in the harness).
- `needsWork(r, ready, now)` adds: `if ((r.tries||0) >= CAP || (r.next_try_at||0) > now) return false;`.
- A list passed explicitly to `startRun(codes)` (the per-reel buttons) still bypasses `needsWork`.

### The night queue: mixing in old reels (D-A2)
A new pure function, `nightQueue(reels, ready, now, max)` in local.js, replaces the filter/sort/slice at local.js:622-623. It keeps the existing `rereadOk` filter.
- **Queue A:** never-tried reels, `byUsefulThenNewest`.
- **Queue B:** all candidates, oldest `added_at` first; due retries come in here too.
- The night takes **3 from A, then 1 from B**, without duplicates, up to `max`. So about 25 % of each night goes to the oldest work.
- The manual Start keeps `byUsefulThenNewest`, but skips parked reels and reels that are not yet due.

### What is shown
- **Reel page:** "Tried 2 times, last on 14 Nov: <last_fail>. Next try after 17 Nov." When parked: "Stopped trying after 3 tries: <last_fail>." A **"Try again now"** button (`#retryReel`) sets `tries=0` and `next_try_at=0`, then calls `startRun([code])`, the same pattern as `#ytagain` at local.js:867.
- **Inbox, "what needs you":** "N reels could not be finished", leading to a filtered list with **"Try all again"**.
- **Start screen:** "N reels wait for a retry; M stopped after 3 tries."

### Interplay
- **Task 2a (stale refusal):** the failure fields go in the same `saveDb()` after each reel (local.js:568). If that save is refused, `staleReload` drops the change, so a reel can get **at most one extra attempt** for each stale event. That is acceptable. Do not merge counters.
- **Task 2b (handover; not merged; NightGuard is on its branch):** the handover stops the run with `stopAllWork`, which never counts. The app and the night never run `startRun` at the same time.
- **Old app versions:** they ignore the four fields and keep them (`{...d}`, whole reel objects). They will retry parked reels as before, which is harmless. The R4 fixtures prove this.

### Tests (phone harness, `tests/test_retry_cap.py`; fake `RN.generate` that always rejects, and a fake clock via `Date.now` override)
- **Five runs** give generate calls 1, 2, 3, 3, 3, with the clock advanced past each `next_try_at`.
- A **Stop** or **slow down** leaves `tries` unchanged.
- **Battery stop** (`stopAllWork`) leaves `tries` unchanged.
- **Success** clears the fields.
- **Try again now** resets and runs exactly one reel.
- **Circuit breaker:** 10 waiting reels and a broken model give exactly 3 generate calls.
- **`nightQueue`** with 1,000 waiting and max 200 includes the 50 oldest.
- **Old library:** a reel without the fields loads, and the fields round-trip through an R4 fixture.
- **Stale refusal** during a failure does not raise `tries` by more than 1.

## Risks
- A wrong `needsWork` change could stop all work, or park good reels. Opus review; the circuit breaker; manual "Try all again".
- The fixture generator depends on old pages running under today's fake RN. Old bridge methods may be missing; the fake must stay tolerant.
- `newerScreen` is reachable only from future versions, so it is tested with the `newer` fixture only.
- Crash loops (a native crash in `generate`) are not capped by v1 (A1-3).
